# 셸

모델의 `Bash` 와 런타임의 훅 명령이 샌드박스에서 어떻게 돌고, 셸 상태가 명령 사이에 어떻게 이어지는지 정한다. 셸 상태 파일 ·
래퍼 · 셸 락 · 트레일러 · 명령 종류 · 취소 · 출력 상한 · 훅 실행과 실행 디렉터리가 이 문서의 몫이다.

> [셸 엔진](workspace-sandbox-shell-engine.md) · [notice](workspace-sandbox-notices.md) · [프로바이더](workspace-sandbox-provider.md) ·
> [보안](workspace-sandbox-security.md) · [설정](workspace-sandbox-configuration.md) ·

## 1. 지속 셸

### 1.1 셸 상태는 샌드박스 안의 파일이다

지속 셸은 프로세스가 아니라 샌드박스 안의 상태 파일 `/workspace/.aimon-shell/{h(shellKey)}/state` 다. `SandboxShell` 은
명령마다 프로바이더의 `run`(OpenSandbox 에서는 `/command`)을 한 번 부르고, 셸 상태는 이 모듈이 직접 이어 붙인다.
프로바이더 SPI 에는 지속 셸 세션이 없다([프로바이더 §2](workspace-sandbox-provider.md)).

OpenSandbox 의 세션 API 를 쓰지 않는다. 세션 API 는 명령 하나를 죽이면 세션 전체가 닫히고, stdout 과 stderr 를 합치며, 출력
상한과 실행 uid 를 받지 않는다. 세션은 execd 메모리에 있어 execd 가 재시작하면 사라진다. 상태 파일로 두면 노드가 바뀌어도
레코드에 쓸 것이 없다.

셸 상태의 키는 shellKey 다 — 세션의 루트 실행은 `session:{sessionId}`, 포크는 `exec:{executionId}` 다(정하는 규칙은
[바인딩 §3](workspace-sandbox-binding.md)). 에이전트 이름 단위로 두지 않는다 — 같은 에이전트의 다른 세션이 cwd 를 공유하게 된다.
턴 단위로 두지 않는다 — 턴마다 cwd 가 초기화되어 모델이 매번 `cd` 부터 다시 한다. 셸 세션 id 를 워크스페이스 레코드에 기록하지
않는다. 레코드가 셸 수만큼 커지고 CAS 경합이 늘며, 노드가 옮겨 가도 앞 노드의 명령이 쥔 세션에 다시 붙게 된다. 상태 파일과
샌드박스 안 락이 같은 일을 더 적은 비용으로 한다.

### 1.2 상태의 수명

상태는 샌드박스와 수명이 같다. 레코드에 셸 참조가 없으므로 노드가 바뀌어도 같은 파일을 읽어 cwd 가 이어지고, execd 가
재시작해도 파일 시스템이 살아 있으면 영향이 없다. **(계획 — 구현 단계 7)** pause/resume 도 같은 이유로 상태를 잃지 않는다.

generation 이 바뀌면 파일도 사라진다. 그때 명령은 기본 cwd · 환경으로 돌고, 모델은 그 사실을 notice 로 한 번 듣는다
([notice §4](workspace-sandbox-notices.md)). 셸 상태는 최선 노력(best-effort) 상태다 — 잃어도 정확성이 깨지지 않는다.

명령은 execd 의 uid 로 돌고 상태 파일도 그 uid 의 것이다. 그래서 같은 샌드박스의 실행끼리는 서로의 상태 파일을 읽고 쓸 수
있다. 같은 샌드박스가 한 신뢰 도메인인 이유다([바인딩 §6](workspace-sandbox-binding.md)).

### 1.3 이어지는 것

이어지는 것은 **cwd 와 export 된 환경 변수뿐**이다. export 하지 않은 셸 변수 · alias · 함수 · `set -o` 는 다음 명령으로 넘어가지
않는다. 서술자 notes 가 이 사실을 모델에게 알린다(문구는 [개요 §6.2](workspace-sandbox.md)).

- 상태 파일에는 기본 환경(프로파일 `env`, execd 가 준 변수)과 **달라진** 변수만 저장한다. 기본 환경이 명령마다 상태 파일로
  복사되지 않게 하려는 것이다.
- `ExecutionOptions.workingDirectory` 와 `environment` 는 그 명령만 서브셸(`(cd X && cmd)`)에서 적용한다. `environment` 는
  서브셸 안의 `export` 로 넣고 `ExecSpec.environment` 로 넘기지 않는다. 상태를 바꾸는 것은 모델이 직접 친 `cd` 와 `export` 뿐이다.
- 저장한 작업 디렉터리를 되살리지 못하면 바인딩의 root 로, root 도 없으면 `/workspace` 로 간다. 이때 결과에 명령 notice 를
  붙인다(§10.1).

## 2. 셸 디렉터리와 래퍼

### 2.1 셸 디렉터리

```text
/workspace/.aimon-shell/{h(shellKey)}/
  state        cwd 와 기본 환경과 달라진 export 변수
  lock         flock 대상 — shellKey 마다 한 명령, 노드 사이에서도
  owner        락을 쥔 래퍼의 "{nodeId} {pid} {pid 시작 시각}"
  heartbeat    락 heartbeat 파일 — 락을 쥔 포그라운드 명령의 노드가 activityWriteInterval 마다 다시 쓴다(§3.2)
  run-{id}.cmd / .out / .err / .in / .timedout / .cwd
               모델 명령(포그라운드 · 백그라운드) 하나의 텍스트 · 출력 · stdin · 표지 — run 파일
  run-{id}.manifest / .blob / .in
               훅 실행의 업로드. 인라인 한도를 넘을 때만 생기고 래퍼가 복사한 즉시 지운다(§9)
/workspace/.aimon-shell/.run.{32 hex}/
               실행 하나의 비공개 디렉터리(§9.2)
  d/           실행 디렉터리의 파일
  .stdin       업로드한 훅 stdin(다이제스트 확인 뒤)
  r.cwd        훅 · 격리 실행의 cwd fallback 표지
```

`{h(shellKey)}` 는 shellKey 값의 해시다. `/workspace/.aimon-shell` 은 seed 가 만들고 파일 도구에는 읽기 전용이다
([파일 시스템 §3](workspace-sandbox-filesystem.md)).

**run 파일**은 모델 명령의 실행별 파일이다. 래퍼가 트레일러를 찍기 전에 스스로 지우고, `SandboxShell` 은 트레일러가 없을 때
(타임아웃, 래퍼 실패, 취소)만 지운다. 정상 경로에서는 아무도 그 파일을 읽지 않으므로 명령마다 files API 로 stat · delete 를
부르지 않는다 — 원격 프로바이더에서는 명령마다 HTTP 왕복이 여러 번 늘어난다. 훅과 격리 실행에는 run 파일이 없다(§9.1).

### 2.2 래퍼

래퍼는 **두 bash 프로세스**다. 바깥(outer)은 exec 의 stdout/stderr 를 쥔 채 락 · 워치독 · 트레일러를 맡고, 안쪽(inner)이 상태를
복원하고 명령을 돌리고 상태를 저장한다. 명령이 `exit 3` 이나 `set -e` 로 셸을 끝내도 끝나는 것은 안쪽뿐이므로 바깥은 출력과
그 명령 자신의 exit code 를 싣는다. 한 프로세스로 두면 셸을 끝내는 명령의 EXIT trap 이 run 파일 리다이렉션 아래에서 돌아 출력과
트레일러가 run 파일로 들어가고 exec 는 아무것도 돌려주지 않는다.

모델 명령의 출력은 exec 파이프가 아니라 **실행마다의 run 파일**로 간다. 그래서 `npm run dev &` 처럼 명령이 남긴 자손은 파일을 쥘
뿐 exec 파이프를 붙잡지 않고, exec 가 그 자손을 기다리지 않는다.

모델 명령(포그라운드)의 래퍼가 하는 일은 이 순서다. 래퍼 스크립트 전문은 `ShellWrapper` 가 정본이다.

1. 명령 텍스트를 `run.cmd` 에 적는다(§2.3).
2. `flock` 으로 셸 락을 얻는다. `shellLockWait` 안에 못 얻으면 **exit 75**(락 대기 실패).
3. `owner` 를 기록한다. 실행 디렉터리가 있으면 여기서 비공개 디렉터리에 놓는다(§9.3) — 락 대기 중에는 비공개 디렉터리가 없다.
4. 명령 타임아웃이 있으면 워치독을 띄운다. 워치독은 타임아웃이 지나면 `.timedout` 을 만들고 래퍼의 프로세스 그룹을 SIGKILL
   한다. 락을 얻은 뒤에 시작하므로 락 대기는 타임아웃에 들지 않는다.
5. inner 를 돌린다(stdout → `run.out`, stderr → `run.err`, stdin ← `run.in`, 락 fd 는 닫음).
6. 워치독을 멈춘다. `run.out` 이 사라졌으면 출력을 잃었다는 이유를 stderr 에 적고 **exit 71**(run 파일 소실).
7. `head -c {max}` 로 `run.out` · `run.err` 를 각각 상한까지 내보낸다(§8).
8. run 파일을 지운다.
9. 트레일러를 stderr 에 찍는다(§4).

비공개 디렉터리에 파일을 놓는 단계는 실패하면 **exit 73**(다이제스트 불일치 · 파일 수 불일치)이나 **exit 70**(그 밖의 배치 실패)으로
끝난다(§9.3). 백그라운드 래퍼는 2–4 단계(락 · owner · 워치독)가 없다. 훅 · 격리 실행은 다른 래퍼(스트림 래퍼, §9.1)를 쓴다.

래퍼는 자기 `oom_score_adj` 를, inner 는 그보다 높은 값을 써서 OOM 이 명령 → 래퍼 · 워치독 → execd 순서로 고르게 한다
(순서와 이유는 [보안 §9](workspace-sandbox-security.md)).

래퍼는 bash 3.2 와 POSIX 도구만 쓴다. 래퍼가 기대는 도구는 이미지 계약이 정한다([설정 §4](workspace-sandbox-configuration.md)).

### 2.3 모델 명령은 데이터다

명령 문자열은 작은따옴표로 감싸(`'` 는 `'\''`) 래퍼 스크립트에 값으로만 들어간다. 바깥이 `printf` 내장 명령으로 `run.cmd` 에
적으면 안쪽 bash 가 읽어 `eval` 한다. `eval` 은 안쪽 bash 자신의 프로세스에서 돌므로 `cd` 와 `export` 가 EXIT trap 까지 살아 있다.
그래서 끝의 `# 주석`, heredoc, 짝이 안 맞는 따옴표가 래퍼 문법을 깨지 않고 그 명령 자신의 오류가 된다. 문법 오류는 명령 자신의
0 아닌 exit code 다.

인자 한도:

- Linux 는 인자 하나를 128 KiB(`MAX_ARG_STRLEN`)로 제한하고, exec 의 스크립트 전체가 인자 하나다. 환경 변수 값도 같은 한도다.
- 포그라운드 · 백그라운드 명령은 어느 프로세스의 인자(argv)로도 넘어가지 않는다. 따옴표를 친 명령이 64 KiB 를 넘으면 스크립트에
  넣지 않고 files API 로 `run.cmd` 를 올린다.
- 명령별 환경 변수와 작업 디렉터리는 늘 스크립트에 들어간다. 따옴표를 친 합이 32 KiB 를 넘으면 실행 전에 잘못된 인자로 거부한다.
  그대로 보내면 exec 가 인자 한도에 걸려 "샌드박스에 닿을 수 없다" 로 보이기 때문이다.
- NUL 이 든 명령 · 작업 디렉터리 · 환경 변수 값, 잘못된 변수 이름은 실행 전에 거부한다.
- 훅 · 격리 · 스트리밍 명령은 안쪽 bash 의 인자로 넘어간다(§9.1). 64 KiB 를 넘으면 거부한다.

### 2.4 `__aimon_` 예약과 상태 저장

래퍼 자신의 상태는 `readonly` 인 `__aimon_*` 변수에 두고 저장 · 복원에서 뺀다. **`__aimon_` 접두어는 예약되어 있다.** 명령은
안쪽 bash 의 위치 인자와 변수를 공유하므로, trap 이 명령이 바꿀 수 있는 것을 읽으면 `set -- src` 나 같은 이름의 변수로 저장 위치를
바꾸거나 저장 범위를 넓힐 수 있다. 저장 위치 · 기준 환경 스냅숏 · 모드는 `eval` 전에 `__aimon_*` 에 복사해 `readonly` 로 묶고,
저장 함수는 인자를 받지 않는다.

- 저장은 내장 명령과 `command -p mv` 만 쓴다. 명령이 바꾼 `PATH`(비워도)나 도구 이름의 함수가 저장을 깨지 않는다. `builtin` ·
  `command` 라는 이름의 함수는 지운다. 저장이 실패하면 임시 파일을 지운다. 저장은 임시 파일에 쓴 뒤 옮기는 원자적 교체다.
- 저장은 명령의 `IFS` 와 무관하다(`local IFS`).
- 명령이 켠 `set -x` · `set -v` · `set -T` 와 DEBUG · RETURN trap 은 저장 과정을 출력에 흘리지 않는다. EXIT trap 이 먼저 그것들을
  조용히 끈다. `set -v` 에서만 한 줄짜리 EXIT trap 문자열이 명령의 stderr 에 남는다.
- `__aimon_save` · `builtin` · `command` 를 재정의하거나 trap 을 지우는 명령은 저장을 막을 수 있다. 셸 상태는 최선 노력이므로
  받아들인다.

## 3. 직렬화와 락

### 3.1 같은 shellKey 의 명령은 직렬화한다

노드 로컬 락이 한 노드 안의 순서를 정하고, 샌드박스 안의 `flock` 이 노드 사이를 막는다. 세션은 코어의 `SessionLease` 로 한
노드에만 있지만, lease 가 옮겨 간 뒤에도 옛 노드의 명령이 아직 돌 수 있으므로 노드 로컬 락만으로는 부족하다. 락을 잡는 것은
포그라운드 명령뿐이다(§5).

**락은 래퍼 bash 만 쥔다.** 모델 명령은 `9>&-` 로 락 fd 를 닫은 채 돈다. 그렇지 않으면 `./gradlew` 의 데몬이나 `npm run dev &`
처럼 명령이 남긴 자손이 fd 를 물려받아 명령이 끝나도 락이 풀리지 않는다. 래퍼가 끝나면(정상 종료든 kill 이든) 락은 커널이 푼다.

연결이 캐시에서 퇴출되면 그 샌드박스의 노드 로컬 셸 세마포어와 스테이징 락을 지운다. 쥐거나 기다리는 스레드가 없는 항목만 지운다
— 도는 명령의 락이 바뀌지 않게 하려는 것이다.

### 3.2 락의 기록 — owner 와 락 heartbeat 파일

래퍼는 락을 얻으면 `owner` 에 `{nodeId} {pid} {pid 시작 시각}` 을 적는다. `nodeId` 는 프로세스 기동마다 새로 뽑는다(호스트명 +
기동 UUID). 재시작한 노드가 옛 자기 명령을 "지금 내 명령" 으로 오인하지 않게 하려는 것이다.

**락 heartbeat 파일**(`heartbeat`)은 락을 쥔 포그라운드 명령의 노드가 `activityWriteInterval` 마다 files API 로 다시 쓴다. 래퍼는
건드리지 않는다. 락을 잡지 않는 명령(백그라운드 · 훅 · 격리 · 스트리밍)은 쓰지 않는다 — 쓰면 죽은 노드가 쥔 락이 살아 있는 것처럼
보인다. 락 heartbeat 파일은 레코드의 활동 heartbeat(`lastActivityAt` 기록과 만료 연장)와 다른 것이다. 활동 heartbeat 는
[수명 §5](workspace-sandbox-lifecycle.md) 가 정한다.

owner 와 락 heartbeat 파일은 지금은 기록만 하고, 죽은 노드의 락을 넘겨받을 때(§3.4) 쓴다.

### 3.3 셸 락 대기

같은 shellKey 의 앞 명령을 `shellLockWait`(기본값은 [설정 §2](workspace-sandbox-configuration.md)) 동안 기다린다.

- **락 대기는 명령 타임아웃에 넣지 않는다.** 모델이 준 타임아웃은 락을 얻은 뒤부터 센다. 래퍼가 락을 얻은 시각부터 명령 타임아웃을
  스스로 재고, `ExecSpec` 의 타임아웃(대기 최후 방어선)은 명령 타임아웃 + `shellLockWait` + 5초다(§5.1).
- 같은 노드의 앞 명령이 `shellLockWait` 안에 끝나지 않으면 "이 세션의 다른 명령이 셸을 쓰고 있다" 에러로 답한다. 명령은 띄우지
  않는다.
- 샌드박스 안의 `flock` 이 `shellLockWait` 안에 풀리지 않으면(exit 75) `owner` 를 읽어 "셸이 다른 노드의 명령에 쓰이고 있다"
  에러로 답한다. 락을 쥔 쪽의 heartbeat 가 살아 있든 아니든, 지금은 락을 넘겨받지 않는다. 죽은 노드의 프로세스 그룹을 끝내는 코드는
  한 노드에서 검증할 수 없으므로, 검증하지 않은 kill 코드를 두지 않고 멀티 노드 시나리오와 함께 넣는다.

### 3.4 죽은 노드 락 인계 (계획 — 구현 단계 6)

`flock` 이 `shellLockWait` 안에 풀리지 않으면 `owner` 와 락 heartbeat 파일을 본다.

- 기록된 pid 가 살아 있고 시작 시각이 같은지(`/proc/{pid}/stat`) 먼저 확인한다. pid 재사용으로 엉뚱한 프로세스를 죽이지 않게 한다.
- 래퍼가 살아 있는데 락 heartbeat 파일이 `3 × activityWriteInterval` 보다 오래됐으면 그 래퍼를 가진 노드는 죽은 것으로 본다. 래퍼의
  프로세스 그룹을 끝낸 뒤 락을 가져오고, 명령 notice("previous command from another node was terminated")를 붙인다.
- heartbeat 가 살아 있으면(다른 노드가 아직 명령을 돌리는 중) 기다리지 않고 "셸이 다른 노드의 명령에 쓰이고 있다" 에러를 돌려준다.

같은 셸에 두 노드가 동시에 쓰는 일은 없다.

## 4. 트레일러와 결과 판정

### 4.1 트레일러

트레일러는 래퍼가 stderr 끝에 찍는 결과 줄이다. 앞에 `\n` 이 있는 한 줄이고, 실행마다 JVM 이 고른 무작위 nonce 로 시작한다.

| 실행 | 형식 | 출력 |
|---|---|---|
| 모델 명령(포그라운드 · 백그라운드) | `\n{nonce} exit=N out=BYTES err=BYTES cwd=0\|1\|2` | run 파일을 `head -c` 로 자른 것. `out` · `err` 는 자르기 전 바이트 수 |
| stream 실행(훅 · 격리 · 스트리밍) | `\n{nonce} exit=N cwd=0\|1\|2` | exec 자신의 스트림. 바이트 수 없음 |

`exit` 는 명령 자신의 exit code 다. `cwd` 는 저장된 작업 디렉터리를 되살리지 못해 root 로 갔으면 1, root 도 없어 `/workspace` 로
갔으면 2 다. `SandboxShell` 은 트레일러를 떼어 내고, 모델 명령은 `out` · `err` 로 잘림을 판단한다. 잘림을 출력 바이트로 판단하지
않는 것은 프로바이더가 출력을 정규화할 수 있기 때문이다([프로바이더 §2](workspace-sandbox-provider.md)).

stream 실행의 트레일러는 끝이 아니라 nonce 표지에서 맞춘다. kill 이 닿기 전에 자손이 stderr 에 더 쓴 것은 버린다. 트레일러
감시자(`TrailerWatch`)는 stream 이 흐르는 동안 트레일러를 찾아 파싱한 값을 기억한다. 그래서 훅이 프로바이더 쪽 캡처 상한(§8)보다
많은 stderr 를 써서 프로바이더가 트레일러를 잘라도 훅 자신의 결과(예: exit 2)가 그대로 나온다. 잡힌 stderr 에 온전한 트레일러가
없으면 기억한 트레일러를 쓴다.

### 4.2 판정 순서

트레일러가 있으면 명령은 스스로 끝난 것이다. 트레일러가 없으면 명령이 끝까지 가지 못한 것이고, 왜 그런지를 이 순서로 정한다
(`SandboxShell.await`).

**취소 → 샌드박스 소실 → 타임아웃 → 락 대기 실패(exit 75) → 무결성 실패(exit 73) → run 파일 소실(exit 71) → 그 밖의 래퍼 실패**

- **취소** — 취소 신호가 걸렸으면 가장 먼저 본다. 이때도 트레일러가 있으면 정상 결과다 — kill 이 닿기 전에 명령이 스스로 끝났다.
  트레일러가 없으면 `ShellCancelledException` 이다. 이 판정은 타임아웃과 샌드박스 소실보다 앞선다. 종료 요청이 execd 에 닿지 못해
  명령이 타임아웃에서 끝나도, 취소 중에 샌드박스를 잃어도 취소로 보고한다(§6.4).
- **샌드박스 소실** — 활동 heartbeat 가 샌드박스를 잃었다고 보고 명령을 kill 했으면 트레일러와 상관없이 소실 에러다.
- **타임아웃** — 프로바이더의 대기 최후 방어선이 지났으면 타임아웃이다. 모델 명령은 트레일러가 없고 `.timedout` 이 있으면
  타임아웃이다. stream 실행은 `.timedout` 이 아니라 JVM 의 시계로 정한다 — 트레일러 없이 137 로 끝났고 명령 타임아웃이 지났으면
  타임아웃이다. 에이전트가 쓸 수 있는 곳의 표지는 위조할 수 있기 때문이다.
- **락 대기 실패** — 포그라운드 래퍼의 exit 75 다(§3.3).
- **무결성 실패** — 비공개 디렉터리가 있는 실행의 exit 73 은 `RunDirectoryIntegrityException` 이다(§9.3). 명령의 `exit 73` 은 이
  조합을 만들 수 없다 — 끝나는 것은 inner 뿐이고 outer 는 여전히 트레일러를 찍는다. 같은 uid 의 프로세스가 outer 를 죽이면 73 이
  아니라 시그널 코드가 된다.
- **run 파일 소실** — 명령이 `.aimon-shell` 을 지워 run 파일이 사라진 경우의 exit 71 이다. 래퍼 실패로 보고하되 출력을 잃었다는
  이유를 싣는다. 빈 성공(exit 0)으로 보고하지 않는다.
- **래퍼 실패** — 그 밖은 래퍼 실패 `ShellExecutionException` 이고 래퍼의 stderr 를 싣는다. 프로바이더가 명령을 끝낸 원인
  ([셸 엔진 §5](workspace-sandbox-shell-engine.md))이 있으면 메시지 앞에 둔다.

stream 실행은 같은 원칙을 이렇게 적용한다: 트레일러 → 무결성 실패(exit 73) → 프로바이더가 끝낸 명령의 원인(kill 원인) → 시계로 정한
타임아웃 → 래퍼 실패. 프로바이더의 kill 이 시계보다 앞선다 — 줄 상한 kill 의 종료가 마감 뒤에 떨어져도 프로바이더의 것이다.

취소로 끝났는지는 신호 플래그가 아니라 래퍼의 트레일러가 정한다. 플래그만 보면 같은 순간에 스스로 끝난 명령을 KILLED 로 잘못
보고하고 실제 종료 코드와 출력을 버린다.

JVM 이 스스로 `kill()` 한 경우(인터럽트, 대기 최후 방어선, 샌드박스 소실)는 무엇이 돌아왔든 그 판정이 먼저다.

알려진 한계: inner bash 가 끝난 뒤 outer 가 워치독을 멈추기 전에 워치독이 터지면, 제때 끝난 명령도 타임아웃으로 보고된다. 그 창은
닫지 않고 받아들인다.

## 5. 명령 종류

### 5.1 한 표

**포그라운드**는 백그라운드 · 훅 · 격리가 모두 아닌 실행이다. 스트리밍은 따로 고르는 종류가 아니라 리스너를 준 호출이고, 포그라운드면
거절한다.

| 종류 | 무엇인가 | 셸 락 | 셸 상태 읽기 | 셸 상태 저장 | 출력 | 타임아웃 | exec 최후 방어선 | 락 heartbeat 파일 | `transientOutput` |
|---|---|---|---|---|---|---|---|---|---|
| 포그라운드 | 모델의 `Bash` | 잡는다 | 읽는다 | 한다 | run 파일, 샌드박스 쪽 `head -c` | 워치독 | 타임아웃 + `shellLockWait` + 5초 | 쓴다 | 끔 |
| 백그라운드 | `ExecutionOptions.background` — `Bash(run_in_background=true)` | 없음 | 읽는다(시작 시점) | 안 함 | run 파일, 샌드박스 쪽 `head -c` | 백그라운드 상한(§7) | 타임아웃 + 5초 | 안 씀 | 끔 |
| 훅 | `ExecutionOptions.isHook()` — 스킬이 선언한 셸 훅 | 없음 | 읽는다 | 안 함 | exec 스트림(스트림 래퍼), JVM 이 자름 | 워치독, 시계로 판정 | 타임아웃 + 5초 | 안 씀 | 켬 |
| 격리 | `isIsolated()`(훅이면 `isHook()` 과 함께) — `hooks.json` 명령, 셸 엔진 | 없음 | **읽지 않는다** | 안 함 | exec 스트림(스트림 래퍼), JVM 이 자름 | 워치독, 시계로 판정 | 타임아웃 + 5초 | 안 씀 | 켬 |
| 스트리밍 | 리스너를 준 호출 — 백그라운드 모니터 | 없음 | 읽는다(격리면 읽지 않음) | 안 함 | exec 스트림, 줄마다 리스너로 | 워치독, 시계로 판정 | 타임아웃 + 5초 | 안 씀 | 켬 |

- 포그라운드 스트리밍 호출은 거절한다. stream 경로에는 셸 락도 상태 저장도 없으므로, 포그라운드 명령의 `cd` 와 `export` 를 말없이
  잃는 대신 거절하는 것이다. 백그라운드 · 훅 · 격리 스트리밍은 허용한다. 모니터는 백그라운드로 부르고, 셸 엔진은 격리 스트리밍을
  쓴다.
- 타임아웃이 `null` 이면 코어의 정의대로 타임아웃이 없다. 워치독을 두지 않고, `ExecSpec` 에는 프로바이더가 요구하는 최후 방어선으로
  하루를 준다.
- `transientOutput` 을 켠 실행은 끝난 뒤 프로바이더가 샌드박스 안에 남긴 출력 사본을 지운다
  ([프로바이더 §2](workspace-sandbox-provider.md)). stream 실행의 출력은 exec 자신의 스트림이어서 프로바이더의 사본(OpenSandbox 의
  execd 스풀)이 샌드박스 안에 남는 유일한 사본이다. 그래서 이 실행들에만 켠다. 포그라운드 · 백그라운드 명령은 출력이 run 파일로
  가고 래퍼가 지운다. 그 사본이 왜 문제인지는 [셸 엔진 §6](workspace-sandbox-shell-engine.md).
- `SandboxShell` 이 선언하는 셸 기능: 파이프 · 리다이렉션 · 취소(`CANCELLATION`) · 격리 실행(`ISOLATED_EXECUTION`) · 실행 디렉터리
  (`RUN_DIRECTORY`) · 스트리밍(`STREAMING`).

### 5.2 백그라운드

백그라운드 명령은 셸 상태를 **읽기만** 하고(시작 시점의 cwd · 환경 변수) 락 없이 돈다. 그래서 같은 shellKey 의 다음 명령이 기다리지
않는다. 락이 없으므로 대기 최후 방어선에 `shellLockWait` 를 더하지 않는다. 상한과 heartbeat 는 §7.

### 5.3 훅

훅 명령은 백그라운드 명령과 같은 길로 돈다 — 세션의 cwd · 환경 변수에서 시작하고, 락을 기다리지 않고, 상태를 저장하지 않는다. 훅은
모델의 명령 사이에 런타임이 끼워 넣는 것이라 모델의 셸을 잡을 이유가 없다. 훅의 `cd` · `export` 는 코어가 넘기는 `AIMON_*` 변수
때문에 서브셸에서 돌아 셸 상태에 남지 않는다.

다른 점은 워치독이다. 래퍼가 포그라운드와 같은 워치독을 띄워 명령을 훅 액션의 타임아웃에서 끝낸다. exec 최후 방어선(타임아웃 + 5초)에만
맡기면 훅이 5초 늦게 끝난다. 타임아웃이 코어의 훅 정책 시한 이상이면 코어가 훅에 건 바깥 시한과 같은 순간이라 둘이 경주한다.

훅이 샌드박스에서 돌 때의 보안 의미(어디서 도는가, 가드의 fail-closed, 좁히기이지 경계가 아님)는 [보안 §6](workspace-sandbox-security.md).

### 5.4 격리

격리 실행은 세션의 상태를 **읽지도 않는다.** 코어는 운영자의 `hooks.json` 명령을 실행 중 이벤트(`preTool`, `postTool` …)에서 그
실행의 환경으로 보내며 `isIsolated()` 와 `isHook()` 을 함께 켜고, 셸이 `ISOLATED_EXECUTION` 을 선언하지 않으면 명령을 돌리지
않는다. 격리 명령은 훅과 같은 길(락 없음, 저장 없음, 워치독)로 돌되, 안쪽 bash 가 `iso` 모드로 상태 파일을 읽지 않고 새 셸처럼
root 에서 시작한다(root 가 없으면 같은 fallback). 명령별 작업 디렉터리가 있으면 그리로 간다. 환경은 기준 환경(프로파일의 exec 환경,
execd 가 준 변수, `GIT_SSL_CAINFO`)과 명령별 변수뿐이다.

이유는 정책 훅이다. 훅의 명령이 세션의 cwd · export 에서 시작하면 모델이 `PATH` · `BASH_ENV` · `LD_PRELOAD` 를 export 하거나 `cd`
해서 자기를 감시하는 운영자의 훅을 조종할 수 있다. 스킬이 선언한 훅은 스킬 자신의 코드이므로 세션 상태에서 시작한다. 기능을
선언하고 지키지 않는 셸은 코어가 알아챌 수 없는 프로바이더 버그다.

셸 엔진(코어 `ExecuteCode`)은 훅이 아닌 격리 실행을 쓴다. 이 실행만 프로바이더가 끝낸 명령의 원인을 예외가 아니라 결과로 받는다
([셸 엔진 §5](workspace-sandbox-shell-engine.md)).

### 5.5 스트리밍

`SandboxShell` 은 코어의 `VirtualShell#execute(command, options, ShellLineListener)` — 백그라운드 모니터가 명령의 출력을 줄마다 받는
경로 — 를 구현한다. 새 래퍼는 없다. 스트리밍 명령은 격리가 아니면 **훅 명령의 stream 경로**를, 격리면 격리 경로를 탄다. 락도 상태
저장도 없고, 워치독이 타임아웃을 지키며, 출력은 exec 자신의 스트림으로 온다.

- 트레일러는 stderr 에 있으므로 stdout 은 명령의 출력 그대로다. 프로바이더가 `OutputSink` 로 넘기는 stdout 조각을 줄로 나눠
  리스너에 넘긴다(`OutputSink` 계약은 [프로바이더 §2](workspace-sandbox-provider.md)).
- 개행 없이 64 KiB 를 넘는 출력은 UTF-8 문자 경계에서 잘라 한 줄로 넘긴다. exec 가 끝나면 남은 꼬리를 넘기고, 그 뒤에 늦게 도착한
  출력은 버린다.
- **stderr 도 흐른다.** stderr 조각은 트레일러 감시자와 함께 두 번째 줄 분할기로도 가서 `onStderrLine` 에 넘어간다. 래퍼의 트레일러
  줄은 실행의 것이지 명령의 것이 아니므로 빼고 넘긴다. 모니터는 이것으로 실패한 명령의 **마지막** stderr 줄을 알린다 — 결과의
  stderr 는 앞에서부터 상한까지만 남는다.
- stdout 과 stderr 의 리스너 호출은 한 번에 하나다. 프로바이더가 두 스트림을 다른 스레드에서 넘길 수 있기 때문이다.
- 결과의 stdout 은 다른 stream 실행과 똑같이 상한까지만 남는다(§8). 취소는 `RunningCommand.kill()` 로 프로세스 그룹을 죽인다(§6).
- 줄 경계는 프로바이더마다 다를 수 있다. OpenSandbox 의 동작은 [OpenSandbox §3.2](workspace-sandbox-opensandbox.md).
- 트레일러 뒤 kill 유예 때문에 늦게 오는 마지막 줄은 잃을 수 있다(§9.5).

## 6. 취소와 kill

### 6.1 kill 은 그 명령의 프로세스 그룹만 끝낸다

데드라인, 스레드 인터럽트, 취소 신호(`ExecutionOptions.getCancellation()`)가 오면 `RunningCommand.kill()` 로 **그 명령의 프로세스
그룹만** 끝낸다 — 래퍼, 명령, 그룹에 남은 모든 자손. 기다리던 쪽만 포기하고 명령은 계속 도는 상태를 만들지 않는다. 코어의
`tools.bash` 패키지 문서가 금지한 동작이다. 프로바이더가 kill 을 지키는 계약은 [프로바이더 §2](workspace-sandbox-provider.md),
OpenSandbox 가 그것을 어떻게 집행하는지는 [OpenSandbox §3.2](workspace-sandbox-opensandbox.md).

- SIGKILL 로 끝나면 `trap` 이 돌지 않고, `kill()` 의 SIGTERM 은 안쪽 bash 의 TERM trap 이 저장을 끈 채 끝낸다. 어느 쪽이든 그 명령의
  `cd`/`export` 는 반영되지 않고 직전 상태가 남는다. 셸을 통째로 잃지 않으며, 결과에 명령 notice("the command was killed; its
  cd/export were not applied")를 붙인다.
- 워치독은 자기 `sleep` 까지 거두므로 짧은 명령이 이어져도 프로세스가 남지 않는다.
- **그룹 밖은 최선 노력이다.** 명령이 `set -m` · `setsid` 로 자기 그룹에 둔 작업은 샌드박스가 사라질 때까지 남는다. execd 도 프로세스
  그룹까지만 끝낸다. 그래도 `CANCELLATION` 을 선언한다 — 선언하지 않으면 모든 명령을 멈출 수 없다. 더 넓은 kill 은 §12.

### 6.2 취소 기능은 무조건 선언한다

`SandboxShell` 은 `ShellFeature.CANCELLATION` 을 무조건 선언하고, 포그라운드와 백그라운드를 가리지 않는다. 프로바이더 SPI 에서
`RunningCommand.kill()` 이 필수이므로 선언이 거짓이 될 프로바이더가 없다. 같은 이유로 취소를 capability 나 새 SPI 메서드로 두지
않는다 — 값이 하나뿐인 손잡이가 되고, init 전 kill 래치까지 갖춘 `kill()` 이 이미 취소 그 자체다.

취소를 실행 스레드의 인터럽트로 바꾸지 않는다. 셸은 그 스레드를 소유하지 않고, 인터럽트에는 "interrupted and killed" 라는 자기 의미가
있다.

### 6.3 언제 신호를 보는가

취소 신호는 명령을 띄우기 전에 **세 번** 본다.

1. `execute` 에 들어오자마자 — 연결 전이다. 띄우지 않을 명령은 프로비저닝도 활동 기록도 하지 않는다.
2. 셸 락을 얻은 뒤.
3. exec 직전.

프로비저닝과 셸 락 대기 자체는 취소로 끊지 않는다. 프로비저닝은 그 슬롯을 쓰는 모든 실행의 것이고 락 대기는 `shellLockWait`
이하라, 각 대기 뒤에 신호를 다시 보는 것만으로 "시작하지 않는다" 가 보장된다.

취소 리스너는 활동 heartbeat 를 시작하기 **전에** 등록한다. 락과 exec 사이에 걸린 신호가 heartbeat 도 활동 기록도 남기지 않게 하려는
것이다. 도는 중에 신호가 걸리면 신호를 건 쪽 스레드가 플래그를 먼저 세우고 `kill()` 을 부른 뒤 돌아온다. 리스너는 던지지 않고
멱등이다. 명령이 아직 없을 때 걸린 신호는 `run` 이 명령을 돌려준 직후 다시 확인해 kill 한다.

### 6.4 결과

- 트레일러가 있으면 정상 결과다(§4.2).
- 트레일러가 없으면 `ShellCancelledException` 이다. 부분 출력은 타임아웃과 같이 run 파일에서 `maxCaptureBytes` 까지 읽는다. 래퍼가
  출력을 내보내고 run 파일을 지운 뒤 트레일러 직전에 죽었으면 exec 스트림에 실린 것을 쓴다. stream 실행은 exec 스트림을 쓴다. 결과에
  명령 notice 를 붙이고, 코어는 그 작업을 `KILLED` 로 둔다.
- 띄우기 전에 걸린 신호면 명령을 띄우지 않고 "cancelled before it started" 로 같은 예외를 던진다. 부분 출력은 없다.
- 종료 요청이 execd 에 닿지 못해도 취소로 보고한다. 명령은 타임아웃(백그라운드는 백그라운드 상한)에서 끝나고, 그때 취소로 보고한다.
- **취소 뒤에 온 인터럽트도 취소로 보고한다.** 코어 스택 종료는 취소하고 5초 뒤 인터럽트하므로, 그러지 않으면 kill 이 느리거나 실패한
  명령이 KILLED 가 아니라 FAILED 로 끝난다. 그때도 명령을 kill 하고 부분 출력을 읽은 뒤 인터럽트 플래그를 되살려 `ShellCancelledException`
  을 던진다. 부분 출력은 플래그를 되살리기 전에 읽는다 — 파일 API 가 인터럽트된 스레드를 거부할 수 있다. 취소 없이 온 인터럽트만
  "인터럽트되어 kill 됨" 실패다.
- 취소 뒤 `await` 가 프로바이더 예외를 던지면 그대로 실패(사용 불가 · 소실)로 올라가고 취소로 바꾸지 않는다. 관찰하지 않은 멈춤을
  주장하지 않는다.
- 셸이 거는 모든 kill 은 실패를 로그로 남기고 삼킨 뒤 명령을 끝까지 기다린다. 던지는 kill 이 실행을 끝내면 아직 도는 명령의 run 파일을
  지우게 된다. kill 은 두 프로바이더 모두 멱등이므로, 취소 리스너와 소실 콜백이 함께 kill 해도 된다.
- 취소 뒤 셸 상태는 명령 전 상태다(§6.1).

코어의 `KillShell` 은 이 경로로 샌드박스의 백그라운드 명령을 끝낸다.

### 6.5 셸 밖의 샌드박스 명령

내용 검색(`rg`)은 취소되면 `rg` 를 끝낸다. 스테이징 검증 · seed · `exec:` 셸 디렉터리 정리도 인터럽트되면 자기 명령을 끝낸다.
`RunningCommand.await` 계약이 요구하는 일이다.

## 7. 백그라운드 명령

백그라운드 명령에는 상한이 둘 있다. 둘은 다른 질문이라 따로 둔다 — **heartbeat 상한**은 그 명령이 슬롯을 얼마나 깨워 두나,
**백그라운드 상한**은 그 명령을 얼마나 돌게 두나다. 둘 다 프로파일 필드이고 기본값은 [설정 §1](workspace-sandbox-configuration.md) 이
정한다.

### 7.1 heartbeat 상한 (`backgroundHeartbeatLimit`)

도는 명령은 그 명령을 가진 노드의 활동 heartbeat 로 슬롯을 깨워 둔다([수명 §5](workspace-sandbox-lifecycle.md)). 백그라운드 명령의
heartbeat 는 `backgroundHeartbeatLimit` 이 지나면 멈춘다. 그 명령은 더는 샌드박스를 깨워 두지 않으므로 개발 서버 하나가 슬롯을 하루
동안 붙잡지 않는다. 그 뒤로는 idle 정책이 평소대로 terminate 한다([수명 §4](workspace-sandbox-lifecycle.md)). 포그라운드 명령은
명령 타임아웃이 상한이므로 따로 두지 않는다.

**예외: 타임아웃이 있는 스트리밍 실행에는 heartbeat 상한을 적용하지 않는다.** 워치독이 끝을 정하므로 도는 동안 슬롯을 깨워 둔다.
그렇지 않으면 한도보다 긴 모니터 밑에서 idle 정책이 샌드박스를 거둔다.

### 7.2 백그라운드 상한 (`backgroundCommandTimeout`)

환경은 코어의 `backgroundCommandTimeout()` 으로 선언한 프로파일의 값을 돌려준다. 늘 값이 있다. 코어의 `Bash` 는 이 값을 백그라운드
명령의 타임아웃으로 쓰고, 시작 응답에서 모델에게 "환경이 이 시간 뒤에 멈춘다" 고 알린다. 이 모듈에 따로 집행하는 코드는 없다 —
코어가 그 값을 명령 타임아웃으로 넘기고, 프로바이더의 대기 최후 방어선(타임아웃 + 5초)이 명령을 끝내 부분 출력을 가진
`ShellTimeoutException` 이 된다.

- 기본값 24시간은 코어가 백그라운드 상한을 갖기 전부터 이 모듈이 허용해 온 길이다. 관찰되는 동작을 조이지 않기 위해서이고, 상한
  도입 때문에 긴 백그라운드 명령이 조용히 짧게 끊기지 않게 한다.
- 백그라운드 상한은 프로파일 단위다. 그 상한이 맞물리는 idle 정책(`terminateAfter` · `backgroundHeartbeatLimit`)이 프로파일 단위이기
  때문이다.
- 상한은 서술자 notes 가 아니라 코어가 백그라운드 시작 응답으로 모델에게 알린다. 서술자는 프롬프트에 렌더되고 그 동등성이 프롬프트
  캐시를 지키기 때문이다.
- 모델은 그 전에 코어의 `KillShell` 로 명령을 끝낼 수 있다(§6).
- 0 이하인 값은 기동 시 거부한다([설정 §3](workspace-sandbox-configuration.md)).

### 7.3 두 상한의 관계

두 상한은 서로 독립이다. heartbeat 상한이 지난 명령은 다른 활동이 있고 없음에 따라 운명이 갈린다. 활동이 없으면 `terminateAfter` 에
샌드박스와 함께 사라져 "샌드박스 소실" 로 끝나고, 활동이 있으면 백그라운드 상한까지 돌다가 부분 출력을 가진 타임아웃으로 끝난다.
명령이 슬롯을 깨워 둘 자격을 잃는 시각에 결정적으로 끝내려는 운영자는 `backgroundCommandTimeout` 을 `backgroundHeartbeatLimit` 과
같게 둔다. 백그라운드 상한이 heartbeat 상한보다 커도 된다.

### 7.4 노드가 죽으면

코어의 백그라운드 작업 목록(`BackgroundBashManager`)은 노드 로컬이다. 노드가 죽으면 샌드박스 안의 명령은 계속 돌지만 결과를 받을
쪽이 없다. heartbeat 가 노드와 함께 멈추므로, 그런 명령은 idle 정책에 따라 샌드박스와 함께 정리된다. 다른 노드가 다시 붙는 길은 §12.

## 8. 출력 상한

`maxCaptureBytes`(코어가 `ExecutionOptions` 로 주는 stdout · stderr 각각의 상한. 주지 않으면 1 MiB)를 어디서 자르는가는 명령 종류에 따라 다르다.

- **모델 명령은 샌드박스 쪽에서 자른다.** 래퍼가 run 파일에서 stdout · stderr 를 각각 `head -c {max}` 로 내보내고 자르기 전 크기는
  트레일러로 알린다. 수십 MB 로그를 JVM 까지 끌고 와서 자르지 않는다.
- `redirectErrorStream` 은 안쪽 bash 의 `2>&1` 이다. 자르기는 합친 스트림에 한다.
- **캡처 상한.** `SandboxShell` 이 프로바이더에 거는 `ExecSpec.maxCaptureBytes` 는 `3 × max + 1 KiB` 다. 프로바이더는 출력을 줄로
  정규화할 수 있고([프로바이더 §2](workspace-sandbox-provider.md)), 잘못된 UTF-8 바이트는 3바이트 U+FFFD 가 되므로 정규화가 스트림을
  최대 세 배로 키운다. 1 KiB 는 트레일러 몫이다. 그래서 래퍼의 `head -c {max}` 를 지난 출력 뒤에 오는 트레일러가 프로바이더 쪽에서
  잘리지 않는다.
- **stream 실행은 JVM 이 자른다.** run 파일이 없으므로 프로바이더 쪽 캡처 상한까지 받은 바이트를 JVM 이 `max` 로 자른다. 정규화하는
  프로바이더에서는 정규화 뒤의 바이트다 — 원래 `max` 바이트였던 출력도 붙은 줄바꿈이나 U+FFFD 팽창 때문에 잘렸다고 보고될 수 있다
  (받아들인 부정확, §12). 스트림 래퍼의 출력을 샌드박스 안에서 `head -c` 로 자르지 않는 것은, 파이프로 걸면 상한을 넘겨 쓰는 훅이
  SIGPIPE 를 받아 동작이 바뀌고 바이트 수를 다시 트레일러로 실어야 하기 때문이다. 프로바이더 쪽 캡처 상한이 이미 JVM 이 받는 양을
  묶는다.
- 타임아웃 · 취소의 부분 출력이 상한보다 길면 `outputTruncated` 를 켠다.
- 프로바이더는 `maxCaptureBytes` 를 넘는 출력을 버리고 잘림만 표시하며 명령을 끝내지 않는다. 예외는 프로바이더의 줄 상한이다
  ([프로바이더 §2](workspace-sandbox-provider.md)). 그래서 줄 하나가 그 상한을 넘는 stream 실행은 끝까지 돌지 못하고 실패한다.
  포그라운드 · 백그라운드 명령은 출력이 run 파일로 가므로 영향이 없다.

## 9. 훅 실행과 실행 디렉터리

### 9.1 스트림 래퍼 — 훅과 격리 실행은 셸 디렉터리에 아무것도 두지 않는다

run 파일은 같은 uid 인 에이전트의 셸이 실행 전에도 도중에도 읽고 고쳐 쓸 수 있다. 정책 훅의 판정(stdout · exit code)을 run 파일로
받으면 에이전트가 그 판정을 위조할 수 있다. 그래서 훅(`hook` 모드)과 격리 실행(`iso` 모드)은 다른 래퍼 — **스트림 래퍼** — 를 쓴다.
스트리밍 명령도 이 래퍼를 탄다. 이것은 좁히기이지 권한 경계가 아니다 — 같은 uid 의 프로세스는 훅이 **도는 동안** 비공개 디렉터리 ·
`/proc/<pid>/fd` · argv 의 nonce 에 닿는다([보안 §6](workspace-sandbox-security.md), uid 분리는
[훅 uid 분리 기록](workspace-sandbox-hook-identity.md)).

- 명령은 `run.cmd` 가 아니라 안쪽 bash 의 여섯째 인자로 간다. 따옴표를 친 명령이 64 KiB 를 넘으면 연결 전에 거부한다 — `hooks.json`
  명령은 짧다. 업로드하고 다이제스트로 확인하는 길은 래퍼를 복잡하게 할 뿐이다.
- stdin 은 정확한 바이트의 base64 를 스크립트에 넣어 `/usr/bin/base64 -d` 로 안쪽 bash 에 파이프한다. 호출자의 charset 그대로의
  바이트가 가고, NUL 도 간다. 따옴표 친 텍스트로 넣으면 스크립트의 인코딩(UTF-8)으로 바뀌어 다른 charset 의 바이트가 달라진다.
  스크립트가 인자 예산(§9.4)을 넘으면 stdin 을 files API 로 올려 비공개 디렉터리로 복사하고, 스크립트에 든 SHA-256 으로 확인한 뒤
  넘긴다.
- 안쪽 bash 의 stdout · stderr 는 exec 자신의 스트림이다. 트레일러는 `exit cwd` 형식이다(§4.1). 상한은 JVM 이 자른다(§8).
- 타임아웃은 JVM 의 시계로 정한다(§4.2). 워치독은 `.timedout` 을 쓰지 않는다.
- cwd fallback 표지는 비공개 디렉터리의 `r.cwd` 에 두고 트레일러로 읽는다.
- 업로드(`run-{id}.manifest` · `.blob` · `.in`)만 `.aimon-shell/{h}/` 에 잠깐 나타나고, 래퍼가 복사한 즉시 지운다.

에이전트가 실행 **전에** 심어 두거나 실행 **사이에** 고쳐 둔 파일은 훅에 닿지 않는다. 스킬 훅은 세션의 셸 상태에서 시작하므로
에이전트가 남긴 cwd · export 는 여전히 닿는다. `hooks.json` 의 격리 실행은 그것도 읽지 않는다(§5.4).

### 9.2 비공개 디렉터리

**비공개 디렉터리**는 실행 하나가 쓰는 0700 디렉터리 `/workspace/.aimon-shell/.run.{32 hex}` 다. "비공개" 는 다른 uid 에 닫혀 있다는
뜻이고, **같은 uid(에이전트의 셸)에게는 열려 있다.** 스트림 래퍼는 늘, 모델 명령은 실행 디렉터리를 받았을 때만 만든다.

- **이름.** JVM 이 따로 고른 난수다. `runPrefix` 의 접미사는 업로드 경로로 실행 전에 에이전트에게 보이므로, 그 이름을 쓰면 에이전트가
  같은 이름의 디렉터리를 미리 만들거나 심을 수 있다. 난수 이름은 exec 의 argv 에서 `mkdir` 직전에야 보인다.
- **만들기.** 래퍼는 먼저 셸 루트(`/workspace/.aimon-shell`)를 `mkdir -p` 로 되살린다. 모델의 명령이 지웠을 수 있고, 그대로면
  `failOpen` 이 아닌 `preTool` 가드가 모든 `Bash` 를 막아 되살릴 길이 없다. 그다음 `umask 077` 아래에서 `mkdir -m 700` 으로
  **배타적으로** 만든다(`-p` 없음 — 이미 있으면 실패). umask 는 배치 동안만 좁히고 명령은 exec 자신의 umask 로 돈다.
- **위치.** `/tmp` 가 아니라 `/workspace/.aimon-shell/` 아래에 둔다. 워치독이 래퍼를 죽이면 JVM 이 files API 로 디렉터리를 지워야
  하는데, 셸이 펼친 `$TMPDIR` 은 JVM 이 알 수 없다. testkit 에서는 명령의 `/tmp` 가 호스트의 `/tmp` 라 정리가 빗나간다. `/tmp` 는
  이미지 계약에도 없고 읽기 전용 루트에서 깨진다. `.aimon-shell` 은 seed 가 만들고 읽기 전용 루트에서도 쓸 수 있다. 같은 uid 가
  닿는다는 점은 어느 위치든 같다.
- `.run.` 접두사는 shellKey 디렉터리(점으로 시작하지 않는다), `run-*` 파일, `exec:` 셸 디렉터리 정리(§10.3)와 겹치지 않는다.
- **지우기.** 래퍼의 에필로그와 `EXIT` trap 이 지운다. 워치독의 `kill -KILL 0` 이 trap 을 건너뛴 경우처럼 트레일러 없이 끝난 실행은
  `SandboxShell` 이 지운다. 지우기 실패는 WARN 로그일 뿐 명령의 실패가 아니다.
- 모델 명령은 비공개 디렉터리를 `flock` 뒤에 만든다. 락 대기 중에는 비공개 디렉터리가 없고, 락이 바쁘면 놓지도 않는다.

### 9.3 실행 디렉터리

**실행 디렉터리**(`ShellFeature.RUN_DIRECTORY`)는 코어가 훅의 파일을 경로가 아니라 바이트로 `ExecutionOptions.getRunDirectory()`
에 실어 보내는 묶음이다 — `hooks.json` 의 `AIMON_HOOK_DIR`(격리 실행), 스킬 훅의 `AIMON_SKILL_DIR`. `SandboxShell` 은 이 기능을
선언한다. 모델 명령의 **run 파일**과 이름이 비슷하지만 다른 것이다.

- **배치 위치.** 파일은 비공개 디렉터리의 `d/` 에 놓이고 그 경로를 변수로 export 한다. 비공개 디렉터리 자신을 export 하지 않는 것은,
  실행 디렉터리에는 코어가 준 경로만 정확히 있어야 하는데 비공개 디렉터리에는 업로드한 stdin(`.stdin`)과 cwd 표지(`r.cwd`)도 있고
  같은 이름의 훅 파일과 부딪힐 수 있기 때문이다. 변수는 다른 명령별 변수 **뒤에** export 해서 같은 이름을 이긴다.
- **인라인과 업로드.** 따옴표 친 base64 와 manifest 가 16 KiB 안이면 스크립트에 넣어 `base64 -d` 로 푼다. 넘으면 files API 로
  **파일 수와 상관없이 두 번** 올린다 — manifest(`run-{id}.manifest`)와, 파일마다 base64 한 줄씩 manifest 순서로 이은
  blob(`run-{id}.blob`). 스크립트에는 둘의 SHA-256 과 파일 수만 싣는다. 그래서 스크립트도 업로드 횟수도 파일 수에 따라 늘지 않는다
  — 작은 파일이 많은 스킬(1 200 개 남짓을 넘으면 manifest 만으로 인자 예산을 넘는다)도 거부되지 않고, OpenSandbox 에서 업로드 한
  번이 `POST` 와 exec 한 번씩이어도 훅 호출마다 드는 왕복이 일정하다. 비밀 파일이 있으면 인라인하지 않고 늘 업로드한다
  ([셸 엔진 §4](workspace-sandbox-shell-engine.md)). 업로드 경로에서 래퍼는 blob 의 각 줄을 `read` 와 `printf` 내장 명령으로
  `base64 -d` 에 넘기므로 바이트가 어떤 프로세스 인자에도 오르지 않는다.
- **배치.** 워치독을 띄우기 전에 한다 — 배치는 락 대기처럼 타임아웃에 들지 않는다. 업로드했으면 둘을 비공개 디렉터리로 복사하고 두
  다이제스트부터 확인한다. 그다음 manifest 의 줄로 경로를, blob 의 줄로 내용을 얻어 파일을 놓는다. 놓는 동안은 noclobber(`set -C`)다
  — 파일 시스템이 하나로 합치는 두 경로(대소문자를 가리지 않는 파일 시스템에서 대소문자만 다른 이름, 같은 이름의 파일과 디렉터리)는
  오류이고 명령은 돌지 않는다.
- **확인.** JVM 이 바이트에서 계산해 스크립트에만 실은 SHA-256 manifest 로 `/usr/bin/sha256sum -c --strict -` 를 돌리고, 파일 수를
  센다. manifest 는 here-document 가 아니라 `printf` 내장 명령의 파이프로 넣는다 — bash 는 here-document 를 `$TMPDIR` 의 임시 파일에
  쓰므로 쓸 수 있는 `/tmp` 가 없는 읽기 전용 루트에서 실패하고, 그 임시 파일이 같은 uid 에 열린 창이 하나 더 생긴다. 빈 실행
  디렉터리는 `d/` 를 만들어 export 하고 다이제스트 확인은 건너뛴다(GNU `sha256sum -c` 는 빈 manifest 를 실패로 본다). 파일 수는
  `-eq 0` 으로 센다. 이 확인은 `/usr/bin` 의 GNU `sha256sum` · `base64` 에 기댄다(이미지 계약,
  [설정 §4](workspace-sandbox-configuration.md)).
- **73 과 70.** 다이제스트가 다르거나 파일이 빠졌거나 더 있으면(`sha256sum` 의 status 1, 파일 수 불일치) **exit 73** →
  `RunDirectoryIntegrityException`. 코어는 `HOOK_FILES_TAMPERED` 로 보고 `failOpen` 과 무관하게 막는다. 그 밖의 배치 실패(디스크, 없는
  도구, `find` 실패, 업로드가 사라짐)는 **exit 70** → 일반 `ShellExecutionException` 이다. 환경 고장을 변조로 보고하지 않는다.
- **연결 전 검사.** 경로에 제어 문자가 있거나, 파일과 디렉터리가 겹치거나, 합이 코어의 `RunDirectory.MAX_TOTAL_BYTES` 를 넘는 실행
  디렉터리는 코어 빌더가 만들지 않는다. 셸은 변수 이름 · 가둠(confined) · 개행 · 합 상한을 연결 전에 다시 검사하지만 방어선일 뿐이다.
  어느 것이든 잘못된 인자이지 무결성 실패가 아니다.
- **모델 명령의 실행 디렉터리.** 모델 명령이 실행 디렉터리를 받으면 그 명령은 서브셸에서 돈다 — 실행 디렉터리 변수가 명령별 변수이고,
  명령별 변수가 있는 명령은 서브셸에서 돌기 때문이다. 그 명령의 `cd` · `export` 는 저장되지 않는다. 코어는 실행 디렉터리를 훅
  명령에만 보낸다.

### 9.4 인자 예산

스크립트 하나가 인자 하나다. Linux 는 인자 하나를 128 KiB 로 묶고, 래퍼 스크립트 전체 — 명령(≤ 64 KiB), 명령별 환경(≤ 32 KiB),
인라인 실행 파일(≤ 16 KiB), 인라인 stdin — 가 그 하나다. 스트림 래퍼는 조립한 스크립트의 길이를 인자 예산(120 KiB)과 견준다.
stdin 을 먼저 업로드로 돌리고, 그래도 넘으면 실행 파일을 업로드(manifest 와 blob)로 돌리고, 그래도 넘으면 연결 전에 거부한다. 다 올린
스크립트는 명령과 환경의 상한 안이므로 마지막 거부는 방어선일 뿐 닿지 않는다. 길이를 조립한 스크립트로 재므로 기존 인라인 상한을
낮출 필요가 없다.

업로드는 연결 뒤, exec 전에 한다. 업로드 실패는 `ShellExecutionException`(파일 시스템 오류) 또는 사용 불가(프로바이더 오류)이고 무결성
실패가 아니다.

### 9.5 훅이 남긴 작업은 훅과 함께 끝난다

스트림 래퍼에서는 exec 의 stdout 이 곧 훅의 stdout 이므로 훅의 `cmd &` 가 exec 를 붙잡는다 — OpenSandbox 의 `await` 는 스트림을 쥔
자손이 모두 끝나야 돌아온다. 그래서 `SandboxShell` 은 exec 가 흐르는 동안 stderr 에서 트레일러를 지켜보다가, 트레일러가 오면 짧은
유예(`TRAILER_KILL_GRACE`, 500 ms — `await` 가 먼저 돌아오면 바로) 뒤에 exec 의 프로세스 그룹을 kill 한다.

**훅이 남긴 작업을 훅과 함께 끝내는 것을 결정으로 둔다.** 기다리면 무언가를 백그라운드로 남기는 훅마다 도구 호출이 대기 최후 방어선
(타임아웃 + 5초)만큼 늘어지고, 그 호출은 도구 호출의 임계 경로에 있다. 대가는 `postTool` 훅의 `notify-send &` 같은 작업이 훅과 함께
죽는 것이다. `setsid` · `set -m` 로 그룹을 떠난 작업은 남는다.

- 트레일러는 `completed` 뒤가 아니라 **흐르는 동안** 감지해야 한다. `await` 는 스트림을 쥔 자손이 모두 끝나야 돌아오므로, 그 뒤에 kill
  하면 결코 제때 오지 않는다.
- kill 은 트레일러를 보면 **무조건** 한다. 두 프로바이더의 `kill()` 은 멱등이라 끝난 exec 에는 비용이 없거나 삼킨 오류뿐이다. `await` 가
  유예 안에 돌아오지 않을 때만 kill 하면, 리더가 끝나면 `await` 가 돌아오는 로컬 프로바이더에서 자손이 살아남아 동작이 프로바이더마다
  달라진다.
- 유예가 있는 것은 execd 가 stdout 과 stderr 를 따로 읽어, 트레일러가 훅의 마지막 stdout 줄(훅의 JSON 판정)보다 먼저 올 수 있기
  때문이다. inner 는 트레일러보다 먼저 그 줄을 썼으므로 그 줄은 이미 execd 의 파이프에 있고, 수백 ms 면 충분하다. 유예보다 늦게 오는
  마지막 줄은 잃을 수 있다 — stdout 과 stderr 를 따로 넘기는 프로바이더에서 스트리밍 실행도 같다.
- kill 은 프로바이더 스레드를 막지 않게 따로 띄운 데몬 스레드가 한다(`OutputSink` 는 막으면 안 되고, OpenSandbox 의 kill 은 HTTP
  호출이다). 트레일러가 `run` 이 돌아오기 전에 오면, 그 스레드는 명령이 생기는 대로 kill 한다.

## 10. 실행 위치와 환경

### 10.1 exec 는 `/workspace` 에서 돈다

exec 의 작업 디렉터리는 `/workspace` 다. seed 가 보장하고 명령이 지울 수 없는 마운트 지점이다. 작업 root 로 들어가는 것은 래퍼다. 명령이
`rm -rf` 로 root 를 지워도 다음 exec 가 "없는 작업 디렉터리" 로 거부되지 않고, 래퍼가 root 대신 `/workspace` 로 물러나며
`cwd=2` 와 명령 notice 를 붙인다. 저장된 cwd 만 사라졌으면 root 로 가며 `cwd=1` 이다. 명령별 작업 디렉터리를 준 명령은 그곳에서 돌았고,
옮겨진 것은 셸의 디렉터리뿐이라는 문구로 알린다.

### 10.2 git 은 exec 환경의 CA 번들을 따른다

셸 래퍼는 `SSL_CERT_FILE` 이 있고 `GIT_SSL_CAINFO` 가 없으면 `GIT_SSL_CAINFO` 를 그 번들로 둔다. Debian 의 git 은 GnuTLS 판 libcurl 을
써서 `SSL_CERT_FILE` 을 읽지 않기 때문이다. OpenSandbox 의 execd 는 egress 프록시의 CA 를 합친 번들을 `SSL_CERT_FILE` 로만 알린다.
기준 환경의 일부이므로 셸 상태로 저장되지 않고, 명령이 둔 `GIT_SSL_CAINFO` 가 이긴다.

### 10.3 `exec:` 키의 셸 디렉터리 정리

`exec:` shellKey 의 셸 디렉터리는 노드 로컬 캐시가 기억한다. 코어 계약상 환경은 실행 끝을 알리지 않으므로, 마지막 명령이 **끝난** 뒤
`execShellIdle`(기본값은 [설정 §2](workspace-sandbox-configuration.md)) 동안 다음 명령이 없는 `exec:` 디렉터리를 캐시가 지운다.
락이 비었을 때(`flock -n`)만 지운다. 노드가 죽어 남은 디렉터리는 수 KB 이고 generation 과 함께 사라진다.

## 11. 실패

도구는 예외를 던지지 않는다. 셸의 실패는 `ShellExecutionException` 계열로 올라오고 코어의 도구가 `ToolResult.error` 로 바꾼다
([개요 §7](workspace-sandbox.md)). 훅 행의 "코어" 열은 코어 훅 실행기가 그 실패를 어떻게 보는지다.

| 상황 | 결과 | 코어 |
|---|---|---|
| 셸 상태 소실(generation 변경) | 기본 cwd · 환경으로 명령을 실행한다. 에러 아님 — notice 는 [notice §4](workspace-sandbox-notices.md) | |
| 명령 kill 로 그 명령의 `cd`/`export` 가 반영되지 않음 | 직전 셸 상태가 남는다. 명령 notice(§6.1) | |

## 12. 열린 질문

- **프로세스 그룹 밖까지 닿는 kill** — 취소와 타임아웃의 kill 은 exec 의 프로세스 그룹까지 닿는다(§6.1). 명령이 `setsid` · `set -m`
  으로 그룹 밖에 둔 작업은 샌드박스가 사라질 때까지 남고, 코어 계약의 "명령이 띄운 모든 것" 을 그만큼 못 채운다. 코어 `LocalShell` 과는
  모양이 다른 한계다 — 그룹째 죽이므로 나중에 태어난 손자 프로세스도 잡지만 그룹을 떠난 작업은 놓친다. `LocalShell` 은 반대로 그룹을
  떠난 자손도 트리로 찾지만 스냅숏 뒤에 태어난 손자는 놓친다. 지금은 그룹보다 넓은 kill 을 하지 않는다 — execd 에 세션 · cgroup kill
  이 없고, `/proc` 순회는 경합하며 모든 자손에 표지를 심어야 하고 취소하는 스레드에서 exec 를 한 번 더 부른다. 업스트림에 요청할지,
  `/proc` 를 훑는 두 번째 exec 로 메울지 정하지 않았다. 넓힌다면 타임아웃 kill 과 함께 하나의 변경으로 한다.
- **백그라운드 명령의 노드 이동** — 프로바이더 쪽 명령 id 를 레코드에 남겨 다른 노드가 다시 붙게 할지는 영속 저장소(구현 단계 6) 이후에
  판단한다. 그때까지의 동작은 §7.4.
- **훅 실행마다의 `DELETE /command`** — 트레일러를 보면 유예 뒤 exec 를 kill 한다. OpenSandbox 의 `kill()` 은 종료 이벤트가 이미 왔으면
  아무것도 보내지 않으므로, `DELETE` 는 유예보다 오래 exec 를 붙잡는 훅 — 스트림을 쥔 자손을 남긴 훅 — 에만 든다. 유예 안에 `await` 가
  돌아오지 않을 때만 kill 하는 길은 로컬 프로바이더에서 자손이 살아남아 동작이 프로바이더마다 달라진다. 이 비용을 받아들일지.
- **남은 `.aimon-shell/.run.*`** — 워치독이 래퍼를 죽인 뒤 JVM 도 죽으면 비공개 디렉터리가 샌드박스가 사라질 때까지 남는다. 다음 실행이
  믿지 않으므로 지금은 둔다. 쓸어 낸다면 seed 나 janitor 가 하되, 다른 노드가 같은 샌드박스에서 훅을 돌리고 있을 수 있으므로 가장 긴 훅
  최후 방어선보다 오래된 것만 지워야 한다.
- **파일 도구가 `.aimon-shell/.run.*` 을 읽을 수 있다** — 셸 상태 영역 규칙은 읽기 전용이지 거부가 아니다
  ([파일 시스템 §3](workspace-sandbox-filesystem.md)). 코어의 실행 디렉터리 계약 범위에서 훅의 바이트는 비밀이 아니지만, 거부 규칙을
  더할지 정하지 않았다.
- **훅 출력의 상한은 정규화 뒤의 바이트로 잰다** — 스트림 래퍼에는 샌드박스 안의 바이트 수가 없으므로, 출력을 줄로 정규화하는
  프로바이더에서는 정확히 `max` 바이트였던 출력도 잘렸다고 보고될 수 있다(§8). OpenSandbox 1.2.0 은 출력을 바이트 그대로 주지만 잘못된
  UTF-8 은 여전히 U+FFFD 로 온다([OpenSandbox §3.2](workspace-sandbox-opensandbox.md)). 정확한 수가 필요해지면 스트림에 샌드박스 안의
  카운터를 붙여야 한다.
