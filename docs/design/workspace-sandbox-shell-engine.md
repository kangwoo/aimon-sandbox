# 셸 엔진 지원

코어의 셸 엔진(Python `ExecuteCode`)이 워크스페이스 샌드박스에서 돌 수 있도록 이 모듈이 지키는 계약을 다룬다. 엔진이 제안되는
조건, `python3` 이미지 계약, 런타임 파일 시스템, 비밀 실행 파일, 프로바이더가 끝낸 명령의 결과 모양, 실행 뒤 아무것도 남지 않는다는
보장이 여기 있다.

> 관련: [개요](workspace-sandbox.md) · [셸](workspace-sandbox-shell.md) · [파일 시스템](workspace-sandbox-filesystem.md) ·
> [프로바이더](workspace-sandbox-provider.md) · [OpenSandbox](workspace-sandbox-opensandbox.md) ·
> [설정](workspace-sandbox-configuration.md) · [테스트](workspace-sandbox-testing.md) ·
> 코어 [셸 엔진 설계](https://github.com/kangwoo/aimon-core/blob/main/docs/design/tool/programmatic-tool-calling-shell.md)

## 1. 엔진이 제안되는 조건

코어의 셸 엔진은 모델이 쓴 Python 프로그램을 샌드박스 격리된 실행 환경의 `python3` 으로 돌린다. 코어가 런타임 · 프로그램 ·
HMAC 키를 실행 디렉터리(`RunDirectory`)로 넣고(키에는 비밀 표지를 단다), 격리 스트리밍 셸 호출 하나로 런타임을 띄우며, 런타임의
도구 호출에는 HMAC 된 응답 파일을 런타임 파일 시스템으로 써서 답한다. 이 흐름은 코어가 소유한다. 이 모듈은 엔진이 기대는 환경
조건을 채운다.

코어는 다음을 모두 갖춘 환경에서만 `ExecuteCode` 를 낸다. 각 조건을 이 모듈이 채우는 방식은 오른쪽 열과 같다.

| 코어가 요구하는 것 | 이 모듈 |
|---|---|
| 서술자의 `isolation() = SANDBOXED` | 늘 싣는다. 조건이 없는 상수이고 포크의 서술자도 같다 — 이 환경의 셸과 파일은 언제나 샌드박스 안이기 때문이다 |
| 서술자의 `runtimes()` 에 `python3` | 프로파일의 선언값을 싣는다(`SandboxProfile.runtimes`, 필드는 [설정 §1](workspace-sandbox-configuration.md)) |
| `runtimeFileSystem()` 이 있음 | 늘 돌려준다(§3) |
| 셸이 `STREAMING` · `RUN_DIRECTORY` · `ISOLATED_EXECUTION` 을 선언 | 선언한다([셸 §5.1](workspace-sandbox-shell.md)) |

서술자 개념 일반은 [개요 §6.2](workspace-sandbox.md) 가 소유한다. 샌드박스를 줄 수 없을 때의 사용 불가 서술자는 코어의 것이고
isolation 을 싣지 않으므로, 코어가 그 환경에 엔진을 내지 않는다(이유 "not sandboxed").

**`runtimes` 는 선언값이지 seed 결과가 아니다.** 서술자는 제안 시점에 프로비저닝 없이 정해져야 하므로 seed 결과를 쓸 수 없다.
seed 가 확인할 수 없는 이름을 받으면 서술자가 지킬 수 없는 능력을 약속하게 되므로, `runtimes` 에는 seed 가 확인하는 이름(지금은
`python3`)만 쓸 수 있다 — 다른 이름은 기동 검사가 거부한다([설정 §3](workspace-sandbox-configuration.md)). 선언, seed 확인(§2),
코어 탐침이 함께 실제 가용성을 지킨다. 선언하지 않은 프로파일은 이미지에 python 이 있어도 서술자에 싣지 않는다.

**제안 판단은 아무것도 프로비저닝하지 않는다.** 서술자, `runtimeFileSystem()` 의 존재, `shell()`, 셸의 `supports` ·
작업 디렉터리는 모두 환경을 만들 때 정해지는 값이고 프로바이더를 부르지 않는다. 게으른 프로비저닝의 원칙은
[수명 §2.3](workspace-sandbox-lifecycle.md) 이 소유한다.

**정적 가용성과 엔진 탐침.** 위 조건으로 정적 가용성이 참이 되면, 코어가 환경 객체마다 한 번 탐침을 돈다 — `python3` 3.8 이상인지,
런타임 파일 시스템으로 쓴 프로브 파일이 셸의 `test -f` 로 보이는지. 탐침이 실패하면 코어는 그 환경 객체에서만 엔진을 뺀다. 탐침이
잡는 경우:

- 프로파일이 `python3` 을 선언하기 **전에** seed 를 마친 슬롯 — 서술자는 프로파일을 읽지만 seed 는 그 검사를 돌린 적이 없다
- 실행 중에 이미지에서 `python3` 이 지워진 경우
- 바인딩 루트가 `/workspace` 밖인 배치 — 런타임 파일 시스템의 가둠(§3)이 프로브 쓰기를 거부한다. 이미지 계약 밖의 배치이므로
  지원하지 않는다

이 조건이 지켜지는지는 [테스트 §5.10](workspace-sandbox-testing.md) 의 시나리오가 확인한다.

## 2. 이미지 계약과 seed 확인

**선택 항목: `python3`(3.8 이상).** 프로파일이 `runtimes: [python3]` 를 선언한 경우에만 요구한다. 선언하지 않은 이미지는 그대로
유효하다. 이미지 계약의 나머지 항목은 [설정 §4](workspace-sandbox-configuration.md) 가 소유하고, 거기서는 이 항목을 한 줄로
가리킨다.

요구하는 것:

- `PATH` 에서 찾히는 `python3`, 버전 3.8 이상
- `python3 -I`(격리 모드)로 코어 런타임(`aimon_ptc.py`)이 맨 위에서 import 하는 표준 라이브러리 모듈이 모두 import 될 것. seed 는
  그 목록을 그대로 import 한다. 목록은 코어 런타임을 따라 고치는 코드 상수다. Debian 의 `python3-minimal` 은 이 목록에 모자라다
- `site-packages` 는 쓰지 않는다(`-I` 가 끈다)
- `TMPDIR`(없으면 `/tmp`)이 샌드박스 사용자에게 쓰기 가능할 것. 런타임은 실행 디렉터리에서 돌지만 모델 코드 출력의 캡처 파일을
  `tempfile.mkdtemp()` 로 만든다. seed 는 이것을 확인하지 않는다(§8)

**seed 확인.** 선언된 경우에만 seed 가 step `runtime-python3` 으로 확인한다. 버전을 먼저, import 를 나중에 본다 — 3.8 미만은 모듈이
다 있어도 다르게 실패할 수 있어서다. step 의 위치(다른 검사와의 순서)는 [수명 §3](workspace-sandbox-lifecycle.md) 이 소유한다.

`runtime-python3` 실패는 영구 실패다. 같은 이미지로 다시 만들어도 결과가 같고, 운영자가 선언을 고치면 프로파일 해시가 바뀌어
FAILED 슬롯이 다시 시도된다. 첫 셸·파일 호출은 다른 이미지 계약 위반과 같은 모양으로 그 실패를 보고한다.

**두 겹 방어.** seed 는 프로비저닝 때 한 번, 코어 탐침은 환경 객체마다 한 번 돈다. seed 는 계약을 벗어난 이미지를 일찍 실패시키고,
탐침은 seed 가 잡지 못하는 경우(§1)를 그 환경 객체에서만 잡는다.

셸 엔진 계약을 어느 계층에서 어느 이미지로 시험하는지는 [테스트 §3](workspace-sandbox-testing.md) 이 소유한다.

## 3. 런타임 파일 시스템

`runtimeFileSystem()` 은 코어 엔진이 응답 파일 · 프로브 파일 · 실행 디렉터리를 쓰고 지우는 프레임워크 전용 파일 시스템이다. 모델의
도구에 주지 않고, 파일 도구의 경로 규칙([파일 시스템 §3](workspace-sandbox-filesystem.md))을 거치지 않는다.

**늘 있고, 묻는 것만으로는 프로비저닝하지 않는다.** 환경 객체는 언제나 이것을 돌려주고, 연산마다 파일 도구처럼 슬롯에 연결한다.
연결 실패(잃은 샌드박스, FAILED 슬롯, 프로바이더 장애)를 포함해 **모든 실패는 `IOException`** 이다. 코어 엔진은 실행 끝의 정리에서
`IOException` 만 잡으므로, 다른 예외가 새면 엔진이 이미 분류한 결과를 예외로 바꿔 버리기 때문이다.

**가둠.** `/workspace/**` 만 받는다. null, 상대 경로, NUL, 빈 · `.` · `..` 성분, 끝의 `/` 는 프로바이더를 부르기 전에 `IOException`
으로 거절한다 — 고쳐 읽지 않고 거절한다. `/workspace` 자체는 읽기와 만들기만 된다. 범위를 코어의 응답 디렉터리
(`<root>/.aimon-ptc/**`)로 좁히지 않는다. 그 이름은 코어의 패키지 전용 상수라 코어가 이름을 바꿀 때 조용히 깨지고,
`/workspace` 가 마운트 계약이자 testkit 이 번역하는 유일한 트리이기 때문이다.

**코어가 기대는 연산.** 엔진은 `createDirectories`, `writeNew`(응답 · 프로브 파일), `delete`(프로브 파일 · 실행 디렉터리)를 부르고
`read` 는 부르지 않는다. 엔진은 `writeNew` 의 `java.nio.file.FileAlreadyExistsException` 을 다른 `IOException` 과 구분하므로(응답
경로가 선점되면 프로토콜 위반) 예외의 **종류**가 계약이다.

| 연산 | 계약 | 남는 위험 |
|---|---|---|
| `writeNew(path, bytes)` | 프로바이더의 새 파일 전용 쓰기(임시 이름에 올린 뒤 링크) — 원자적이고, 이미 있는 파일과 링크(끊긴 링크 포함)를 거절한다. 무엇이든 있으면 `FileAlreadyExistsException`. 프로바이더가 다른 이유로 거절하면 샌드박스 안에서 `[ -e ] \|\| [ -L ]` 로 "무언가 있다" 를 가려 같은 예외로 답한다. 부모 디렉터리는 프로바이더가 만든다(인터페이스는 요구하지 않는다) | 임시 파일은 대상 옆에 있어 같은 uid 가 링크 전에 읽을 수 있다. 부모 성분의 심볼릭 링크는 따라간다 — 무결성은 HMAC 이 지키고, 기밀성은 같은 uid 앞에서 지켜지지 않는다 |
| `read(path, maxBytes)` | 샌드박스 안 도우미 한 번. 링크는 거절하고 따라가지 않는다. 없으면 `NoSuchFileException`, 정규 파일이 아니면 거절, 읽을 수 없는 파일은 빈 결과가 아니라 실패다. `maxBytes` 가 음수면 `IllegalArgumentException`, 16 MiB 를 넘으면 거절한다 — 자르면 "작으면 전부" 계약이 깨지고, 상한이 있어야 캡처 상한을 셀 수 있다. `0` 도 위 검사를 한다 | 링크 검사와 읽기 사이의 TOCTOU. 도우미는 샌드박스 사용자로 돌므로 남는 것은 샌드박스 안의 기밀성이다 |
| `delete(path)` | 샌드박스 안 도우미 한 번 — 지운 뒤 무엇이든 남으면 실패. 마지막 성분의 링크는 따라가지 않고 링크를 지운다(끊긴 링크도) | — |
| `createDirectories(path)` | 프로바이더의 디렉터리 만들기. 디렉터리가 아닌 것이 있으면 `IOException`(nio 하위 타입이 아니다) | — |

`read` 와 `delete` 를 files API 가 아니라 샌드박스 안 도우미로 하는 이유: files API 는 "링크를 따라가지 말라" 를 표현할 수 없고(stat
이 링크를 따라가는지도 확인되지 않았다), `python3` 은 선택 항목이라 쓸 수 없으며, 코어가 쓰지 않는 연산을 위해 프로바이더 SPI 를
늘리지 않는다. 도우미는 2분 안에 끝나야 하고, 출력을 줄로 바꿔 내므로(이미지 계약의 GNU `/usr/bin/base64`) 프로바이더의 줄
상한(§6)에 닿지 않는다. `read` 도우미의 출력은 파일 내용이므로 transient 로 둔다(§6). 쓰기의 링크 도우미는 출력이 없어 transient 로
두지 않는다.

**스레드 안전.** 엔진은 응답을 여러 실행기 스레드에서 동시에 쓴다. 구현은 불변 참조만 쥐고 연산마다 연결하므로 동시 호출에 안전하다.
연결이 만든 notice(초기화 · 재생성)는 환경의 큐에 쌓이고 `ExecuteCode` 의 결과 뒤에 전달된다 — 프로그램을 띄운 셸 호출과
같다([notice §2](workspace-sandbox-notices.md)).

**배치와 정리.** 코어는 `.aimon-ptc/` 를 서술자의 작업 디렉터리(바인딩 루트) 아래에 둔다. 그 배치와 파일 도구가 그곳을 거부하는
규칙은 [파일 시스템 §2 · §3](workspace-sandbox-filesystem.md) 이 소유한다. 엔진이 환경 객체당 첫 실행에서 `.aimon-ptc/` 아래 오래된
항목을 지운다. 샌드박스 쪽 스윕은 없다(§8).

**실패.**

| 경우 | 결과 |
|---|---|
| 연산 중 샌드박스가 사라짐 | 슬롯을 잃음으로 표시하고 `IOException`. 엔진은 `writeNew` 실패를 호스트 실패(`SCRIPT_ERROR`)로 분류하고, 셸 호출은 스스로 실패한다 |
| 연산 전 연결 실패(FAILED 슬롯, 프로바이더 장애, 잃은 샌드박스) | `IOException` — 엔진의 정리 단계가 분류된 결과를 예외로 바꾸지 않는다 |
| 응답 경로를 같은 uid 의 프로세스가 선점(파일 · 디렉터리 · 링크) | `FileAlreadyExistsException` → 코어는 프로토콜 위반으로 다룬다 |
| 업로드는 됐으나 링크 도우미가 다른 이유로 실패 | 프로바이더가 임시 파일을 지우고 `IOException`. 경로에는 아무것도 남지 않는다 |
| `read` 대상이 링크 · 비정규 파일 · 없음 | `IOException` · `IOException` · `NoSuchFileException` |
| 도우미 시간 초과, 프로바이더 오류 | `IOException` |
| 가둠 밖 경로 | 프로바이더를 부르기 전에 `IOException` |

이 계약을 고정하는 계약 스위트(`RuntimeFileSystemContract`)는 [테스트 §1.4](workspace-sandbox-testing.md) 가 소유한다.

## 4. 비밀 실행 파일

**실행 디렉터리에 비밀 표지가 붙은 파일이 하나라도 있으면 실행 파일 전부를 업로드한다.** 스크립트에 인라인하지 않는다. 업로드는
파일 수와 상관없이 manifest 와 blob 두 개라 비밀 파일만 따로 올릴 이득이 없다. 환경 변수와 stdin 도 스크립트에 인라인되어 결국
명령줄(`/proc/<pid>/cmdline`)에 오르므로, 업로드가 argv 노출이 없는 유일한 경로다. 그 결과 스크립트(= execd 의 `bash -c` 인자)에는
비밀의 base64 대신 manifest 와 blob 의 SHA-256 만 남는다.

업로드 경로가 파일 바이트를 어떤 프로세스 인자에도 싣지 않는 메커니즘, 인라인과 업로드를 고르는 일반 순서, 업로드 원본을 지우는
시점은 [셸 §9.3](workspace-sandbox-shell.md) 이 소유한다. 이 절은 "비밀이면 늘 업로드" 라는 정책만 소유한다.

- **비용.** 코어는 `ExecuteCode` 의 실행마다 HMAC 키를 비밀로 표지하므로, 엔진의 실행은 **모두** 업로드 경로를 탄다. 실행마다 exec
  앞에 HTTP 업로드 둘이 더해진다(도구 호출당이 아니라 실행당이다)
- **새로 열리는 실패.** 작은 실행 파일도 업로드되므로 업로드 실패가 셸 실행 실패가 된다. 엔진에서는 `SCRIPT_ERROR` 다
- **남는 창.** 비밀이 업로드된 뒤 래퍼가 그것을 비공개 디렉터리로 옮기고 지우기까지의 창은 남는다. 같은 uid 의 프로세스가 그 사이에
  읽을 수 있다(코어 셸 엔진 설계의 열린 질문)

어떤 cmdline 에도 비밀 바이트가 없다는 것은 [테스트 §5.10](workspace-sandbox-testing.md) 의 시나리오가 확인한다.

## 5. kill 원인

프로바이더는 타임아웃도 호출자의 `kill()` 도 아닌 이유로 명령을 스스로 끝낼 수 있다. 지금 그런 경우는 하나다 — 출력 한 줄이
프로바이더의 줄 상한을 넘을 때(§6). 이 절은 그 사실이 무엇을 뜻하고 셸 결과에 어떤 모양으로 실리는지를 소유한다. SPI 필드
(`ExecOutcome.killCause()`, 함께 서는 잘림 표시, `timedOut` 과의 배타, 프로바이더가 자기 열거형을 두는 이유)는
[프로바이더 §2.5](workspace-sandbox-provider.md), OpenSandbox 프로바이더가 타임아웃과 줄 kill 중 무엇을 기록하는가는
[OpenSandbox §4](workspace-sandbox-opensandbox.md) 가 소유한다.

**뜻.** kill 원인이 실린 명령은 프로바이더가 끊은 것이다. 끊긴 뒤의 출력은 잃었으므로, 래퍼가 끝까지 돌아 트레일러를 남겼더라도
호출자는 스트림을 완전한 것으로 읽으면 안 된다.

**결과 모양.** `SandboxShell` 은 stream 실행의 kill 원인을 이렇게 옮긴다.

| 트레일러 | kill 원인 | 격리 비훅 | 결과 |
|---|---|---|---|
| 있음 | 없음 | 무관 | 트레일러의 결과 |
| 있음 | 있음 | 예 | 트레일러의 결과 + kill 원인 |
| 있음 | 있음 | 아니오 | 트레일러의 결과 |
| 없음 | 있음 | 예 | 프로바이더 결과의 종료 코드(실제로는 137), 잘림 표시, kill 원인을 실은 결과 |
| 없음 | 있음 | 아니오 | 원인을 말하는 셸 실행 예외("the provider ended the command: an output line exceeded the provider's line limit") |
| 없음 | 없음 | 무관 | 셸의 판정 순서([셸 §4.2](workspace-sandbox-shell.md)) |

**격리 비훅**은 격리 모드이면서 훅이 아닌 실행이다. 코어의 훅 실행기도 `hook` 과 함께 `isolated` 를 쓰므로 "격리" 만으로는 엔진의
실행을 가릴 수 없어 훅을 명시적으로 뺀다. 이 정의는 엔진의 실행 모양(격리 + 리스너)과 탐침 모양(격리, 리스너 없음)을 모두 덮는다.
모니터는 리스너를 단 백그라운드 실행이라 격리가 아니다.

결과를 격리 비훅 실행에만 돌려주고 훅 · 모니터에는 예외를 던지는 이유: 코어 엔진은 반환된 결과에서만 `PROTOCOL_VIOLATION` 을
분류하므로(예외는 `SCRIPT_ERROR` 가 된다) 엔진 실행에는 결과가 필요하다. 반대로 넘친 가드 훅이 종료 코드 137 로 돌아오면 코어 훅
실행기가 그것을 판정으로 읽어 도구를 통과시킬 수 있으므로 훅에는 예외가 필요하다. 코어는 엔진이 받은 `LINE_LIMIT_EXCEEDED` 를
`PROTOCOL_VIOLATION` 으로 읽고 그 환경 객체에서 엔진을 끈다.

**판정 순서.** 취소는 판정 전에 정해진다. kill 원인은 실행 파일 변조 판정 다음, 시계 기반 타임아웃 추정보다 **먼저** 본다 — 마감
뒤에 떨어진 줄 kill 을 타임아웃으로 읽지 않기 위해서다. 변조 판정이 앞서는 것은 래퍼가 명령을 시작하기 전에 끝나서 줄 kill 과 겹칠
수 없기 때문이다. 이 단계는 [셸 §4.2](workspace-sandbox-shell.md) 의 판정 순서에 한 단계로 들어간다.

트레일러가 없는 비스트림 실행에서 kill 원인이 오면(실행의 출력에는 트레일러만 있어 예상하지 않는다) 셸 실행 예외의 메시지가 원인을
말한다. 진단용이고 결과 모양은 바뀌지 않는다.

## 6. stream 실행의 출력 사본

훅 · 격리 · 스트리밍 실행(셸 엔진의 실행은 격리 스트리밍이다)에는 프로바이더 SPI 의 두 규칙이 걸린다. 규칙 자체 —
`ExecSpec.transientOutput()` 의 뜻, 이벤트 줄 상한과 그것이 `maxCaptureBytes` "버리되 끝내지 않는다" 의 예외인 이유 — 는
[프로바이더 §2.4 · §2.6](workspace-sandbox-provider.md) 이, OpenSandbox 에서의 줄 상한 초과 처리와 삭제 절차는
[OpenSandbox §4.4 · §4.5](workspace-sandbox-opensandbox.md) 가, 어느 실행에 켜는지는 [셸 §5.1](workspace-sandbox-shell.md) 이 소유한다. 이 절은
셸 엔진이 왜 그 규칙을 필요로 하는지와 그 귀결만 쓴다.

**출력 사본 삭제.** 훅 · 격리 · 스트리밍 실행의 출력은 exec 자신의 스트림이어서 execd 의 스풀이 샌드박스 안에 남는 유일한 사본이다.
그래서 이 실행들에만 transient 출력을 켠다. 모델의 포그라운드 · 백그라운드 명령은 출력이 run 파일(`run.out`)로 가고 래퍼가 지운다.

OpenSandbox 1.2.0 의 execd 는 포그라운드 명령이 끝나면 스풀을 스스로 지운다. 그래도 프로바이더는 transient 실행 뒤 스풀을 지운다 —
stream 실행의 출력 사본이 execd 버전의 정리 동작에 기대지 않게 하기 위한 이중 방어다. 이 삭제는 execd 가 `TMPDIR` 없이 뜬다는
배포 계약에 기댄다([설정 §4](workspace-sandbox-configuration.md), seed 의 확인은 [수명 §3](workspace-sandbox-lifecycle.md)). 삭제는
best effort 이고, 실패해도 명령의 결과는 바뀌지 않는다.

**이벤트 줄 상한.** 엔진 실행의 출력은 모델이 쓴 프로그램이 정한다. 줄 상한이 없으면 개행 없는 출력 하나가 JVM 메모리에 통째로
올라온다. 프로바이더는 받은 이벤트 줄 하나가 상한(256 KiB, 받은 JSON 바이트로 센다)을 넘으면 명령을 끝내고, 그 사실을 kill 원인으로
돌려준다(§5). 엔진에서는 `PROTOCOL_VIOLATION` 이 된다.

이 규칙은 출력을 숨기는 데 쓸 수 없다. 명령이 일부러 긴 줄을 내면 그 뒤의 출력을 잃지만, 결과는 조용한 성공이 아니라 잘림 표시와
kill 원인이다. 같은 uid 의 공존 프로세스가 스풀에 긴 줄을 덧붙여 실행을 끝내게 하는 것은 코어 셸 엔진 설계가 받아들인 실행 방해
(DoS) 위험과 같은 무게이고, 그 프로세스는 어차피 명령을 kill 할 수 있다.

**통로 줄의 분할.** 코어의 통로 줄 상한(64 KiB 미만)은 프로바이더의 줄 상한보다 작아 둘은 충돌하지 않는다. 다만 셸은 리스너에 넘기기
전에 개행 없이 64 KiB 에 이른 줄을 잘라 별도의 줄로 넘긴다(규칙은 [셸 §5.5](workspace-sandbox-shell.md)). 그래서 64 KiB 이상의 통로
줄은 호스트에 두 조각으로 닿고 둘 다 MAC 이 맞지 않는다. 결과는 같은 프로토콜 위반이지만, 호스트가 "줄이 너무 길다" 를 따로
진단하려면 이 분할을 알아야 한다.

## 7. 시간 초과·취소 뒤 남는 프로세스

**시간 초과 · 취소된 `ExecuteCode` 실행은 샌드박스에 아무것도 남기지 않는다.** 코어 런타임의 프로세스 토폴로지가 이것을 보장한다.

- **앵커** — 셸이 띄운 프로세스. exec 의 프로세스 그룹에 남고 비밀을 쥐지 않는다
- **런타임** — 앵커 아래에서 자기 프로세스 그룹을 이끈다
- **워치독** — 런타임이 이중 fork 해 런타임의 그룹에 둔다. 앵커가 죽으면(어떤 신호로 죽든 커널이 앵커의 파이프를 닫는다) 그 그룹을
  죽인다

이 모듈의 kill — 타임아웃 · 취소 · 줄 상한 — 은 exec 의 프로세스 그룹까지 닿는다([셸 §6.1](workspace-sandbox-shell.md)). 앵커가 그
그룹에 있으므로 이 kill 로 충분하다. 이 모듈은 세션 전체 kill 같은 우회를 하지 않는다 — 이미지 계약이 그것을 약속할 수 없기
때문이다.

**좀비 워치독.** 이중 fork 된 워치독은 샌드박스의 PID 1 에 입양되고, 그룹을 죽인 뒤 PID 1 의 좀비가 되므로 PID 1 이 거둬야 한다.
이것은 이미지 계약에 넣지 않는다 — PID 1 은 이미지가 아니라 프로바이더(또는 풀)가 정하기 때문이다.

- OpenSandbox 의 PID 1 은 Docker 런타임과 K8s 템플릿 모드 모두 `bootstrap.sh` 의 `sh` 이고, 진입점을 기다리는 `wait` 가 입양된
  자식도 거둔다. 서버가 `execd_run_as_init = true` 로 뜨면 그 자리에 `execd --init` 이 오고, 이것도 거두는 init 이다. 서버 사실의
  정본은 [OpenSandbox §3](workspace-sandbox-opensandbox.md) 이다
- K8s 풀 모드의 샌드박스는 풀 파드의 task-executor 아래 task 로 돌고, PID 1 은 서버가 아니라 풀이 정한다. task-executor 는 고아를
  거두지 않으므로 그것이 PID 1 이면 좀비가 쌓인다. 거두는 PID 1 을 쓰거나 `execd_run_as_init = true`(execd 가 subreaper 가 된다)로
  풀린다. 운영자가 언제 이 설정을 켜야 하는지는 [설정 §5](workspace-sandbox-configuration.md) 가 소유한다. 지금 풀 모드는 시험
  seam 으로만 요청한다. **(계획 — 구현 단계 7)** 공개 풀 지원은 수명 최적화 단계에서 다룬다(§8)

남은 프로세스 검사가 무엇을 보장하고 어디까지를 보이지 못하는지, 어느 계층(K8s 템플릿 · 풀 모드 포함)에서 도는지는
[테스트 §6](workspace-sandbox-testing.md) 과 [테스트 §3.2 · §3.3](workspace-sandbox-testing.md) 이 소유한다.

## 8. 열린 질문

- **`.aimon-ptc/` 가 모델의 작업 트리 안에 있다** *(코어)* — 코어는 엔진의 실행 디렉터리를 서술자의 작업 디렉터리 아래에 두고, 이
  환경의 작업 디렉터리는 바인딩 루트(기본 `/workspace/repo`)다. 실행 디렉터리는 실행 끝에 지워지지만, 실행 중에 모델이 돌린
  `git status` · `git add -A` 는 응답 파일을 본다. 서술자가 런타임 디렉터리를 따로 선언하거나 작업 디렉터리의 부모를 쓰면 풀린다.
  seed 는 `.git/info/exclude` 로 응답 파일을 가리지 않는다 — seed 는 저장소를 소유하지 않으며(seed 뒤에 모델이 `git init` · clone 할
  수 있다), 모델의 저장소 메타데이터를 바꾸는 것은 예상 밖 동작이다. git seed(**계획 — 구현 단계 5**)와 함께 다시 본다
- **`RuntimeFileSystem` 계약 스위트의 자리** *(코어)* — 코어는 계약 스위트를 발행하지 않아 이 저장소의 testkit 에 두었다. 코어의
  testkit 으로 옮길 수 있다
- **testkit 계층의 엔진 계약 스위트와 `reply_dir`** *(코어)* — 코어 런타임은 응답 디렉터리를 실행 디렉터리 파일(`reply_dir`) 안의
  절대 `/workspace` 경로로 읽고, testkit 의 로컬 프로바이더는 파일 바이트의 `/workspace` 를 번역하지 않는다. 그래서 testkit 계층은
  그 파일 하나를 바꿔 넣는 시험 전용 장식자로 돈다. 런타임이 응답 디렉터리를 환경 변수로 받으면 장식자 없이 돈다
- **`.aimon-ptc` 의 샌드박스 쪽 스윕** — 엔진의 스윕은 환경 객체의 첫 실행에서만 돈다. 오래 쓰지 않은 워크스페이스에는 응답 파일(HMAC
  된 도구 결과)이 남는다. 공유 볼륨에서는 한 슬롯의 seed 가 다른 슬롯의 살아 있는 실행의 응답을 지울 수 있어 seed 에서 지우지 않는다
- **훅 · 모니터가 줄 상한에 걸렸을 때의 모양** — 코어의 `killCause()` 계약은 어느 실행에든 원인을 결과로 싣는 것을 허용한다. 이 모듈은
  격리 비훅 실행에만 결과를 돌려준다(이유는 §5). 범위를 넓힐지
- **seed 가 `TMPDIR` 쓰기를 확인하지 않는다** — 이미지 계약(§2)은 쓰기 가능을 요구하지만 seed 는 확인하지 않는다(`/tmp` 쓰기는
  다른 무엇에도 확인하지 않는다). 지금은 문서로만 둔다
- **풀 파드의 PID 1** *(공개 풀 지원(계획 — 구현 단계 7) 전에 닫는다)* — 거두는 PID 1 또는 `execd_run_as_init` 이 필요하다는 것은
  정해졌다(§7). 남은 것은 공개 풀 지원이 이를 seed 로 확인할지다
